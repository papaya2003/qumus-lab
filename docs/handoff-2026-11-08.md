# Lab-PC handoff — 2026-11-08

## Aim

Make manual L1/L2 commissioning observable on the physical bench: show images, make test travel visible,
record the operator's observations, and continue testing independent devices after ordinary problems.
Distinguish a successful software command from a successful physical action.

This work also changes real motion/voltage limits and fixes driver/reporting bugs. It is not just a
display change, a completed calibration, or proof that the whole system is ready for unattended operation.

## Operator workflow and report fixes

- Fixed a real crash when recording `n`: `ProbeLog.write()` received `step` twice. The observation's
  description now uses `test_step`.
- L2 asks before each action. `s` skips the device's remaining steps. After an action, `y` confirms
  expected behavior; `n` records a problem and skips that device; `q` quits. The `n` choice explicitly
  requires that the instrument is stationary/safe before testing another device.
- Known connection/query/refusal failures skip that device and permit the rest of the walk.
  Unknown outcomes, service locks, command timeouts, stop requests, and unexpected errors still stop
  the walk. No automatic retry or unlock was added.
- Skipping a device also skips its paired return move. Never assume it returned to its starting pose;
  a later run starts from the then-current physical pose.
- Each run prints a summary and writes a timestamped `*-l2-report.json`, including partial results on
  Ctrl+C. The daily `*-probe.jsonl` still appends; restarting does not overwrite it. Some early incomplete
  L2 entries were explicitly cleared at the operator's request; the earlier L1 report was preserved.
- L2 now has 20 steps, including all three camera captures. Interactive Windows captures open their
  saved files in the default image viewer. Focus moves capture before/after microscope images and wait
  the estimated travel time before the after image. Return to the terminal to answer the observation.
- A watched heater test now succeeds only when the heater reports `target reached`. Merely accepting
  the start command no longer makes a below-target timeout look successful.

The existing web dashboard was used, not redesigned. Its jog step menus and 6.5 V heater input maximum
were not expanded to match the larger CLI/L2 tests. Real probe and dashboard processes must not compete
for the same COM ports; closing the browser tab does not stop the dashboard service.

## Driver corrections

### Stamp holder / Kinesis

The old completion loop could see an initially idle cached status immediately after issuing a
nonblocking move and return stale/zero position data. The real backend now requests position updates
and allows polling time. Completion requires idle status plus position within 0.001 mm of target,
stable for at least 0.25 s. Failure to confirm the target times out, requests stop, and reports an
unknown outcome instead of success. Operator checks later reported the larger reversed Z test working.

### Tape gantry / comparison with working v1

The working reference is the sibling `../Qumus` tree on this PC, especially
`common/hardware/printer_controller.py`. It was read and used for emulator comparisons, not edited.
Its defaults and `config/settings.json` also select COM22 at 115200 baud.

Differences found and corrected in `drivers/printer_gantry.py`:

1. V1 sends `M17 X Y Z` at construction. The new driver had deliberately removed motor enable at
   connect but had not enabled motors for L2 jogs. It now enables them before the first explicit motion;
   connection and L1 queries remain free of motor-enable commands.
2. Restored v1's 50 ms pause after command acknowledgement (`command_settle_s`).
3. Position reads now consume the entire `M114` response through `ok`, rather than leaving a late
   acknowledgement that could be mistaken for the next command's reply.

These are verified software differences, **not a confirmed physical fix**. Subsequent real X tests
still failed according to the operator, despite `motors_on: true` and changing reported X coordinates.
A fresh connection repeatedly reported the earlier coordinates again. Do not treat `ok`, `motors_on`,
or `M114` alone as proof of displacement.

Read-only queries on COM22 identified Prusa-Firmware-Buddy 6.1.4 / Prusa-MK4 and reported all queried
endstops open. The physical cable/controller identity is not independently confirmed. `M410` stop
behavior remains unverified; the v1 driver does not use it.

Recommended next investigation: with all competing controllers closed, establish whether the gantry
moves from its own controls and whether v1 still moves it **now**. If v1 works, capture both programs'
real serial exchanges for the same small, operator-confirmed move, including timing and connection/close
behavior. If neither works, investigate controller display errors, motor power and the physical link.
Do not continue guessing axis signs or increasing displacement as a substitute for this comparison.

## Remaining limitations

- Focus position is an estimate reset to zero on connect; no TMCL GAP position query was added.
  The interactive L2 wait is outside the service executor. General API focus moves still return after
  acknowledgement, so the old long-motion supervision limitation now matters more with a 5 mm cap.
- Arm stop confirmation, gantry stop behavior, unknown travel ranges and named-point calibration remain
  open. Existing `source: v1` values are still provisional.
- Heater target timeout is working, but exfoliation warm-up performance still needs measurement.
  Do not automatically increase power or infer a calibrated temperature-control curve from this session.
- Software tests use emulators. Passing them does not override failed operator observations.
